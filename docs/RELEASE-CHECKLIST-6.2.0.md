## 四之二、全量 e2e 里翻出来的两条**用例**缺陷（产品是对的）

> 这两条都是「全量跑才红、单跑是绿的」。按判据 13，先分清产品回归与用例自身 ——
> 这两条都用**确定性**的证据判到了「用例」这一侧。

- [x] **`style-isolation` 的接管提示夹具是坏的**
      → 嵌入框里那个 `<video>` **没有 src、永远暂停**。于是「接管不了」有两种含义，
      而产品分得很清楚：这一层**没有能播的视频** → 什么都不说；
      这一层**有视频但接管不了** → 说「视频在嵌入框里」。用例要的是后者。
      → 实测（真实 Chromium，两次跑对照）：没有源的版本里，`f` 落到哪个 frame
      取决于点击有没有把焦点送进嵌入框 —— **同一份页面，两次结果不同**。
      → 修法：给视频真的 `src` 并让它播起来；再对「点完焦点确实在顶层」加一条断言
      （原来那是**假定**，不是事实）
- [x] **`first-run-hint-reset` 的采样窗口太窄**
      → 重置之后的重来走的是 `scheduleReveal`，也就是**完整**的 `WATCH_DELAY`
      （2.5 秒）—— 产品有意如此：刚关掉引导的人不该在 300ms 后被同一个东西再糊一次脸。
      → 实测（3 次）：引导重新可见的时刻是 **2.15 秒**左右。
      而原来的窗口是 **4000ms** —— 只剩 1.8 秒余量，认领那次跨进程往返稍慢就滑出去。
      → 修法：窗口放到 8000ms。**变异验证过它仍然会红**：
      把「重来」那段短路掉 → 用例红（`弹出来的内容：[]`）。

## 四之三、宿主负载：让「产品坏了」与「机器被压垮了」一眼分开（第十四轮）

- [x] **分诊**（先分清「产品回归」与「测试环境自身」）

## 四之四、「视频在嵌入框里」的提示会看运气（第十五轮，1 条产品缺陷）

> 起因还是那条不稳的用例（`style-isolation` 的「四个提示」，
> 5 次全量里红 2 次）。这次**不是环境** —— 是用户按下 `f` 之后
> 有时候屏幕上什么都不会出现。

- [x] **根因**：background 问一圈的总预算写死成 320ms（两轮广播）。
      而回答的延迟不归我们控制 —— 实测同一份页面：
      空闲 1~2ms；宿主负载 65/12 核时 **545~870ms**；
      再让嵌入框主线程忙 600ms → **830~1450ms**。320ms 之外的回答被直接丢掉
- [x] **换判据**（不是把数字调大）
      → 放弃条件 = 「没有任何 frame 报『我能接管』」或「总预算（1.8 秒）用完」
      → 预算上限由内容脚本那侧的查询节流（2 秒）决定，再长会叠出两轮长等待
      → 一有可用回答**立刻收工**（否则放宽预算 = 每次成功都白慢 250ms）
      → 「有人答了」判据从 `reports.length > 0` 改成「有没有**能接管**的回答」
      （一个 frame 说「我没有视频」只证明它活着）
- [x] **死区**：第一版「一轮 250ms + 休息 80ms」，落在缝里的回答没人听
      → 实测 1/3 才出现；改成首尾相接后 5/6（剩下的尾巴是宿主被压垮）
- [x] 新增 3 条单测 + **2 条变异验证**（逐条验过）
      → ① 只问一轮 → 「晚到」「旁观 frame」两条同时红；
      ② 摘掉「立刻收工」→ 只有那一条红（隔离正确）
- [x] `video-owner.spec.js` 的反向断言从等 1.2 秒提到 **2.6 秒**
      （结论现在要等总预算用完才下得出来；1.2 秒断言是恒真的守卫）
- [x] 探针用完即删（`zzprobe-takeover-path.mjs`、`zzprobe-blocked-frame.mjs` → 已删）
- [x] 判据写进 `ARCHITECTURE.md` **判据 16**：产品里的「超时」也不能拿来当结论
- [x] **`style-isolation` 那条用例自己也要能分诊**（四段链路，四种故障长得一样）
      → 按键前在主世界装一个 keydown 计数器，在 background 装一个只读观察者
      （只记 `vsc-video-owner-*` 三类消息）
      → 失败信息现在会一起带出：顶层 `activeElement` / keydown 条数 /
      嵌入框视频的 `paused`、`readyState`、`videoWidth` / background 收到的协议消息
      → 顺着这条把**前置条件**也补严了：原来只要求 `!paused`，
      而 `play()` 之后 `paused` 立刻为 false、**此时可能一帧都没解码**
      （`readyState: 0`）。现在要求 `paused=false && readyState≥2 && videoWidth>0`
- [x] ⚠️ **已知残留（诚实记录）**：修完之后全量 e2e 跑了两轮，
      **175/176（1 条红）** 与 **176/176**（host 饱和度 6.17~8.08 / 6.69）。
      那条红就是本条用例，失败信息是「按 f 之后提示没出现」，
      而它**单跑 19/19、4 路并发 4/4、加强前置条件后 3/3 全绿**。
      没有复现出确定性的产品复现路径 —— 按判据 15，这一类先记成
      「宿主被压垮 + 用例自身判据不严」，**两条补丁（预算 + 前置条件）都已经打上**，
      下次若再出现，失败信息里会直接写明是哪一段断的（不再是一句「没出现」）
