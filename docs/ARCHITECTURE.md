# 架构文档

本文档描述当前代码库（v6）的真实结构。

## 目标

当前实现聚焦六条主路径：

- 目标视频选择（打分制）
- 网页全屏 + 全屏控制条（字幕等浮层随视频一起进出）
- 播放速度控制（快捷键步进 + 长按连续）
- 播放控制（播放/暂停、快进快退）
- 设置持久化与热更新（仅快捷键）

## 模块总览

```text
Content Script（注入到**每一个** frame，见「帧的归属」一节）
  └── ContentRuntime
      ├── VideoRegistry          # 选对视频
      ├── KeyboardController     # 7 个可绑定动作
      ├── FullscreenController   # 全屏生命周期（含浮层搬运）
      │     ├── FullscreenControls  # 全屏内极简控制条（住 shadow root）
      │     │     └── ControlsStyles  # 控制条自己的样式（shadow tree 里，页面样式进不来）
      │     ├── OverlayLayers       # 探测字幕 / 弹幕等覆盖在视频上的浮层
      │     ├── SubtitleOffset      # 字幕避让位移（可精确还原站点自己的 transform）
      │     └── FrameExpander     # 把装着播放器的 iframe 撑满顶层视口（6.2.0）
      ├── AmbientPreview         # 「装饰性自动播放」的判据（注册表与引导共用一份）
      ├── BodyObserver           # 「body 被站点换掉」的观察（注册表 / 胶囊 / 引导共用一份）
      ├── SpeedToast             # 极简调速提示（胶囊淡出后留下常驻小角标）
      ├── TakeoverNotice         # 接管不了时的诚实反馈
      ├── FirstRunHint           # 首次使用引导（一次性）
      ├── TransientPill          # 上面两条共用的提示骨架
      ├── ViewportRoot          # 浮层的唯一挂载点（<html>，不是 <body>）
      ├── LiveRegion             # 读屏播报通道（视觉上不可见的 live region）
      ├── FrameScope             # 「用户此刻在哪个 frame」的判据
      └── RuntimeStyles          # 注入到页面的那份 <style>（控制条的不在这里）

Background (service worker)
  ├── 工具栏图标点击 -> 向「用户此刻聚焦的那一个 frame」发 TOGGLE_FULLSCREEN
  ├── 记住每个标签页此刻聚焦的 frame（内存 + storage.session）
  └── 原生命令 open-options -> 打开设置页

Options Page
  └── 7 个动作的快捷键绑定（保留键硬拦 + 草稿/已保存分离）
      ├── options-reserved   # 浏览器保留键清单 + 扩展自己的命令键
      └── options-platform   # 平台感知的快捷键显示（macOS 的 ⌘）

Shared
  ├── shortcuts   # 规范化 / 匹配 / 保留键检测
  ├── domMatches  # 元素与选择器的匹配（页面能改坏 matches / closest → 统一退化）
  ├── settings    # storage.sync 读写 + 旧版迁移 + 引导状态（local）
  ├── i18n        # chrome.i18n + 中文回落
  ├── rate        # 倍速格式化（内容脚本与 background 共用的纯函数）
  └── types       # 设置模型与默认值（单一来源）
```

## 内容脚本

### `ContentRuntime`

文件：`src/content/runtime.ts`

职责：

- 安装运行时样式
- 加载设置，失败时回退默认
- 启动注册表与键盘控制器，订阅设置变化热更新
- 启动时清掉 6.0.7 废弃的站点速度表（`vsc-site-speeds`）
- 响应 background 的 `TOGGLE_FULLSCREEN`（工具栏图标点击）
- 把注册表的 `getWatchedTarget()`（视频 + 它能吃下哪些键）喂给键盘控制器

#### 启动顺序：先注册监听器，再 await 设置

`start()` 的顺序不是随意的：

1. `installRuntimeStyles()` —— 样式要**先**落地，否则用户会看到一帧没样式的提示；
2. `prepareLiveRegion()` —— 读屏播报的容器要在第一条播报之前就位
   （`document_start` 时可能还没有 `body`，于是再补一次 `DOMContentLoaded` 重试）；
3. **注册 `chrome.runtime.onMessage`** —— 这一步必须在 `await loadSettings()` **之前**：
   background 的「谁有视频」广播是**一发**的，而设置加载要读一次 `chrome.storage`，
   机器一忙就能迟几十毫秒。先注册，这一层才答得上话（见「帧的归属」一节）；
   紧接着把「倍速变了」与「焦点在哪」的监听也挂上（它们同样不依赖设置）；
4. `await loadSettings()`；
5. `registry.start()` → `keyboardController.start()` → `firstRunHint.start()`；
6. 上报焦点与倍速。

⚠️ 上报倍速前要先过 `ownsUserFocus()`（见 `frameScope`），
而且**判据要在去重之前** —— 否则一次被挡下的上报会把去重的时间戳一起吃掉，
下一次真的该报的时候反而被当成「没变过」。

### `VideoRegistry`

文件：`src/content/videoRegistry.ts`

职责：

- 扫描普通 DOM、Shadow DOM、同源 iframe 中的 `video`
- 记录最近交互的视频与「用户最后一次**亲手**选它」的时间戳
- 按**打分制**选主：各档权重**相加**取最高分（**不是**一条 `A > B > C` 的排序链）
- 帧号 + MutationObserver 的一帧内快照缓存，避免每次按键全页遍历
- 观察 `document.body` 的增删（经 `BodyObserver`）—— 站点把 body 整个换掉时，
  观察器跟着换到新 body 上，并作废全部缓存（否则快捷键会永远醒不过来）

#### 打分制（`scoreCandidate`）

各档**相加**后取最高分。写成「最近交互 > 正在播放 > 可见性 > …」会造出一句假话 ——
两档之间可以互相抵消，没有固定先后：

| 档 | 分值 | 说明 |
| --- | --- | --- |
| 用户刚碰过它 | +10000 | 有时限（新鲜期），过期后不再占位 |
| 键盘刚命中它 | +8000 | 让接下来的按键继续命中同一个视频（图标与快捷键必须指向同一个） |
| 站点适配器的**优先集**（`selectors`） | +1600 | ⚠️ 这**不是**「站点主播放器」—— `mainSelectors` 只决定空格键归谁，**不参与打分** |
| 正在播放 | +600 | |
| 可见 | +300 | |
| 在视口内 | +200 | |
| 面积 | `Math.min(面积, 1_000_000) / 1000` | **上限 1000**（一百万像素²），大视频不会无限加分 |

⚠️ 面积那一档上限 1000，**压得住**「正在播放」的 600 ——
一个占满视口的大视频可以凭面积赢过正在播的小预览。

#### 两个查询，两套契约

注册表对外暴露**两个**目标视频查询，契约不同，**不能混用**：

| 查询 | 语义 | 用于 | 找不到时 |
| --- | --- | --- | --- |
| `getCurrentVideo()` | 「页面上最可能是目标的视频」 | **显式**操作：点工具栏图标 | 返回 null（并给出「接管不了」反馈） |
| `getWatchedTarget()` | 「用户此刻正在看的视频」+ **它能吃下哪些键** | **隐式**操作：快捷键 | 返回 null → **按键完全穿透给页面** |

这条分界是 6.0.9 最重要的行为变更。此前两者是同一个函数，于是只要页面上
存在任何 `<video>`，空格/方向键就在**整页**生效 —— 用户在读长文（页面里嵌了
个静音的自动播放预览视频），按空格翻页结果视频跳了。这是唯一会让人直接卸载的问题。

#### 「正在看的」怎么判定

按**证据强度**分层，命中任一即算（`isWatchedVideo`）。**判定顺序不是随意的**：
不依赖布局的判据必须排在依赖布局的判据前面 —— 在没有布局引擎的环境里
（单测的 jsdom）rect 全是 0，把布局判据放前面会把候选**误杀**，
「没有布局就放行」的兜底根本轮不到执行。

1. **用户显式选过它**（60 秒内，暂停也算）→ 一定是。任何推断都推不翻用户自己的手势。
   ⚠️ 但用户**滚走了**它就另说（信息流里点第 1 条 → 滚到第 2 条，
   第 1 条还在后台播放，却已经不是用户此刻在看的东西）。
2. **站点点名的主播放器**（`siteAdapters.ts` 的 `mainSelectors`）→ 是。
   YouTube 的主播放器是静音自动播的（浏览器只允许静音自动播），
   所以「静音自动播」本身不能当排除依据 —— 只有站点能指名谁是主播放器。
   ⚠️ 「还在视口里」这一条不能省：主播放器滚出视口之后，
   页面上的内容才是用户此刻在看的东西。
3. **排除**：站点的**装饰性预览**（`isAmbientPreview`，**七条**证据全中才算）。
4. **无布局引擎** → 到此为止，返回 true（不能因为「量不出尺寸」就把候选全判死）。
5. **排除**：CSS 隐藏、可见面积不足视口的 10%。
6. **排除**：不够大（`isProminent`：宽 ≥ **400** 且高 ≥ **225**，**或**占视口 ≥ 10%）。

#### 装饰性预览：七条证据，而不是一个属性

⚠️ **这份判定只有一份**（`src/content/ambientPreview.ts`）。曾经它散在两个文件里
并且**已经漂移**：`videoRegistry` 那份被重写成「六条证据」（当时的说法；如今是**七条**，见下），
`firstRunHint` 那份
还停在最老的属性判据（autoplay + 无 controls）。后果是同一条视频，两边给出
**相反**的结论 ——「要不要接管它」说不是装饰（接管了，键盘能用），
「要不要给它弹引导」说是装饰（引导永远不出现）。于是在任何用自制播放器的网站上：
用户能调速，却从来不知道这扩展会做什么 —— 而引导是这个产品**全部的可见入口**。

修法不是「把两边抄成一样」，而是**只留一份**。规则在 `ambientPreview.ts`，
而「用户碰过」「站点自己开的」这两条**证据**只有 `VideoRegistry` 知道
（它们靠事件与手势的时间关系判定，别人算不出来），所以由
`registry.isAmbientPreview(video)` 代答。

6.0.9 的判据是「`autoplay` 属性 + 没有原生 `controls`」—— 一个**属性**判据。
它错得很具体：爱奇艺主播放器的真实形状就是 `<video class="full" autoplay muted>`、
1353×671、占视口 70.1%、无 controls，与文章页里那种装饰性预览**在 DOM 上完全一样**。
于是爱奇艺整页失键（实测 `=` / `Space` / `f` 全部无反应，扩展等于没装）。

现在判据是**七条证据全中**才算装饰。七条**分属三个地方**，
所以「谁提供」这一列比「证据」本身更重要 —— 拼装的地方是
`VideoRegistry.computeAmbientPreview`：

| # | 证据 | 谁提供 | 为什么是排除依据 |
| --- | --- | --- | --- |
| 1 | 站点没有点名它是主播放器 | `ambientPreview.ts` 的 `isDecorativeAutoplay`（`isMainPlayer`） | 站点比我们清楚 |
| 2 | 不是我们正在接管着的那个 | 同上（`isTakenOverByUs`） | 自己做的事不算「站点弄的」 |
| 3 | 用户从未亲手碰过它 | 同上（`wasChosenByUser`）—— 证据只有 `VideoRegistry` 知道 | 用户碰过 = 用户要的 |
| 4 | 没有原生 `controls` | 同上 | 站点把它当播放器给人用 |
| 5 | **是站点自己开的**（`autoplay` 属性，或站点调 `play()` 且此前无用户手势） | 同上（`wasStartedBySite`）—— 证据只有 `VideoRegistry` 知道 | 没人开过它 → 用户正要「先调速再播放」 |
| 6 | 它不是**页面主角**（占视口 < 60%） | `ambientPreview.ts` 的 `isPageMainContent`（独立导出） | 装饰性预览不会霸占大半个屏幕 |
| 7 | **键盘刚命中过它** | `videoRegistry.ts` 的私有证据 `wasTargetedByKeyboard` | 用户正在用快捷键调它，不该当成装饰物丢掉 |

⚠️ 第 7 条为什么只有 `VideoRegistry` 知道：它是「我们自己打分打出来的结果」
（`keyboardTargetVideo`），别人算不出来 ——
所以判定链的**终点**必须在 `VideoRegistry`，`FirstRunHint` 只能问它。

「谁开的」这条是让「先调速再播放」这条最常见的用法继续可用的关键：
它和装饰性预览在 DOM 上可以一模一样，却能被区分开。
另有一处启动期追记（`catchUpSiteStartedVideos`）：扩展注入在 `document_start`，
而 `registry.start()` 要等设置加载完，中间那几十毫秒里页面已经可能 `play()` 了，
那次 play 事件我们听不到 —— 不补这条，文章页预览照样被接管。

#### 「部分接管」：空格可以还给页面

判定出「用户正在看的视频」之后，还要再判一次**它能吃下哪些键**
（`resolvePermission` → `TakeoverPermission`）：

- `'full'`：它正在播 / 有原生 controls / 是站点主播放器 / 用户 10 秒内选过它。
- `'no-space'`：以上都不是。**空格放行给页面**（用户要翻页），
  其余键（`=` / `-` / `0` / 方向键 / `f`）照常作用在它身上。

这条是「部分接管」而不是「接管或不接管」：文章页里那个被站点 JS 启动的
大预览，用户按 `=` 调速是合理的（他看着的就是它），但按空格期望的是翻页。
键盘控制器在解析出目标之后、执行动作之前判这个信号
（见 `KeyboardController` 一节的「部分接管」）。

#### 「用户选过」必须伪造不了

第 1 条是最高优先级的证据，所以「用户选过」这件事本身必须**伪造不了**。
实测下来有三条路，都堵上了：

| 攻击手法 | 为什么不拦得住 | 现在的做法 |
| --- | --- | --- |
| 页面 `dispatchEvent(new PointerEvent('pointerdown'))` | 扩展在 `document_start` 抢注捕获阶段监听器，页面能往自己的 video 上打合成事件 | 合成事件一律不算（`isTrusted`） |
| 页面 `video.focus()` | 焦点是**浏览器**生成的，`focusin` 的 `isTrusted` 恒为 true，isTrusted 挡不住 | `focusin` 只记录「最后碰过的视频」，不参与「用户选过」 |
| 页面在用户按任意键后的 2 秒内让自己的视频播起来 | 「最近一次手势」原先只看**时间** | 手势必须**指向某个具体的视频**（落在它身上，或它是视口中心附近且够大的那一条） |

另外，「用户选过」的新鲜度必须**与视频绑定**（`lastChoiceVideo` + `lastChoiceAt` 成对）。
原先只有时间戳，于是用户点了视频 A 之后、站点让预览视频 B 自动播 ——
B 白白继承了 A 的新鲜度，被判成「用户选过」。

#### 目标不能漂移

多视频页面上「正在播 +600」这一档会让目标**漂移**：用户刚用空格暂停了 A，
A 立刻失去 600 分，还在播的 B 变成最高分，下一次按键就打到 B 身上。
实测：两个 600×338 同时在播 → `=` 命中 cam1 → 空格暂停 cam1 → `f` 却把 cam2 搬进了全屏。

所以另有一档 `keyboardTargetVideo`（**独立字段**，30 秒窗口，+8000 分）：
指针信号（+10000）永远压过键盘信号，键盘信号压过「在播」（+600）。

⚠️ 它**不能**写进 `lastInteractedVideo` —— 后者的语义是「用户用指针碰过的最后一个视频」，
键盘写进去会盖掉指针信号，而且它永不过期。
但打分是**两条路径共用**的，所以工具栏图标与快捷键仍然指向同一个视频 ——
「图标和快捷键表现不一致」是 6.0.9 修掉过的缺陷，不能再引回来。

#### 布局判据的一个坑

`hasReliableLayout` 判断「这个文档有没有布局几何」，判据是**根元素的
`clientWidth`**（真实浏览器恒等于视口宽度，无布局引擎的环境恒为 0）。

⚠️ 曾经用「元素的 computed `display` 是否为空」来判 —— 那是个隐蔽的错：
扩展自己注入的 `runtimeStyles` 里有 `.vsc-page-fullscreen-video { display: block }`，
于是**一进全屏**判定就从「无布局」翻成「有布局」，接下来所有 rect 判定（此时恒为 0）
开始生效，视频被判成「看不见」→ **全屏里快捷键彻底失灵**。
根元素的 `clientWidth` 不受任何页面样式影响，判据本身是稳的。

#### 判定必须对「我们自己造成的变化」免疫

`isAmbientPreview` 认的是「没有原生 `controls`」。而进网页全屏时我们会
`video.controls = false`（用自制控制条取代原生控件）—— 这会**反射性地移除
`controls` 属性**。于是进全屏后，一个正经播放器会被误判成「装饰视频」→
快捷键失灵。

修法：视频已经在我们的 overlay 里躺着时，它不可能是「站点的装饰视频」。

⚠️ 这类「自己把自己判出局」的坑只能靠**真实浏览器**测出来 ——
jsdom 里 `controls` 属性的增删不影响任何断言。

#### 判定必须穿透 shadow tree

「这个视频还挂在文档里吗」不能用 `ownerDocument.contains(video)` ——
**`Document.contains()` 不穿透 shadow tree**，于是所有 shadow DOM 里的
`<video>` 一律被判成「已从文档移除」，**完全不被接管**。

实测（真实 Chromium）：960×540、带 controls 的 shadow-DOM 播放器 →
按 `=` / `ArrowRight` / `f` 三个键全部无效。

```
document.contains(shadowVideo)  = false
host.contains(shadowVideo)      = false
shadowRoot.contains(shadowVideo) = true
video.isConnected                = true   ← 正确判据
```

`Node.isConnected` 走的是「连着文档树」这条真实链路，shadow tree 在内。

### `KeyboardController`

文件：`src/content/keyboardController.ts`

职责：

- 只认设置页里绑定的键；留空 = 该动作禁用
- 忽略输入框、文本域、可编辑区域、输入法合成中
- 全屏内 `Escape` 退出（不需要有视频）
- 处理速度长按重复；失焦/页面隐藏时兜底清理定时器
- 优先挂到 `content-loader` 在 `document_start` 注册的桥接监听器，
  保证先于所有页面脚本，不被抢跑或吞键

#### 键的所有权：一个按键到底归谁

扩展在 `<all_urls>` 上以 **window 捕获阶段**监听每一个 `keydown`。
一个按键可能同时被三方需要：站点、浏览器默认行为、我们。
判定按**从窄到宽**的顺序，一层一层问，任何一层说「归你」就到此为止：

| 层 | 判据 | 放行范围 |
|---|---|---|
| 1. 编辑态 | 焦点在文本框 / 文本域 / `contentEditable` / ARIA textbox 类角色 | 全部按键 |
| 2. 焦点所在控件 | 焦点在 `button` / `a[href]` / `input[type=range\|checkbox\|radio\|button]` / `summary` / ARIA `button\|slider\|…` | **该控件自己会用的那几键**（range 的方向键与 Home/End/PageUp/PageDown；button/link 的空格与 Enter） |
| 3. 我们自己 | 焦点在 `#vsc-controls` 里的控件 | 同上（空格 / Enter / 方向键） |
| 4. 我们的快捷键 | 键匹配设置页里的绑定，且页面上有「用户正在看的视频」 | 吞掉并执行 |

**为什么第 2 层不能省**：「视频够大、正在被接管」与「焦点落在哪个控件上」是
**两条独立的轴**，不能用前者去推断后者。实测（真实 Chromium）：

- 焦点在**站点自己的** range 滑块上按 `→` → 滑块 `value` 纹丝不动、`input`
  事件 0 次，而视频 `currentTime` 从 0 跳到 5 —— 滑块在键盘下彻底失效；
- 焦点在**站点自己的**按钮上按空格 → 按钮 `click` 次数 0（没触发），
  视频反而开始播放 —— 空格是 `<button>` 的标准激活键。

**为什么第 3 层必须有**：我们在捕获阶段 `preventDefault()` 掉的空格，
会让浏览器「空格激活按钮」的默认行为一起消失。实测：焦点在**我们自己**
控制条的静音/退出按钮上按空格 → 静音没触发、全屏没关，反而把视频切成了播放。
`=`、`-`、`0`、`f` 仍然归我们 —— 浏览器对这些键没有默认行为。

判定焦点所在元素必须用 `composedPath()[0]` 而不是 `event.target`：
键盘事件跨 shadow 边界时 `target` 会被重定向成宿主元素。

#### 长按（`event.repeat`）不重复执行动作

物理按键按住期间，浏览器会持续派发 `keydown`（`event.repeat === true`）。
这些重复事件**不能重复执行动作**：

| 动作 | 重复执行的后果（实测） |
|---|---|
| 空格（切换播放/暂停） | 视频每 ~120ms 闪一次 |
| `→`（快进 5 秒） | 按住一秒跳过约 150 秒 |
| `f`（进出全屏） | 全屏进进出出地闪 |

但**要不要吞掉**这些重复事件，必须与**第一次按下**保持一致：

- 第一次按下时页面上没有视频 → 键本来就该给页面（长按 = 滚动页面）；
- 第一次按下时我们接管了 → 长按期间页面不该动。

所以判据是 `holdOwner`（上一次我们接管了哪个动作），而不是「这次有没有视频」。

只有「加/减速」是例外：它们本来就有刻意的连发机制
（延迟 280ms + 每 120ms 一次，由 `startRepeat` 驱动），与浏览器自己的按键重复无关。

#### 先判键，再查视频

「查视频」不是一次轻量判断：它要扫遍全页的 DOM 节点（还要顺带钻进每个
shadow root 与同源 iframe 找里面的 `<video>`），再对每个候选强制算一次
样式和布局。实测（真实 Chromium，3 万节点的页面）单次全页扫描约 **3.2ms**
（纯 `querySelectorAll('video')` 只要 0.2ms）。

扩展注入在 `<all_urls>`，**每一个按键**都会走到这里；而用户按的绝大多数键
（字母、数字、功能键、Ctrl 组合…）根本不是我们的快捷键。
所以顺序必须是：**先匹配绑定 → 是我们的键才查视频**。

#### 部分接管：空格可以还给页面

`getWatchedTarget()` 返回的不只是「是哪个视频」，还有**它能吃下哪些键**
（`TakeoverPermission` = `'full' | 'no-space'`）。判据见 VideoRegistry 一节。

键盘控制器在**解析出目标之后、执行动作之前**判这个信号：
`'no-space'` 且按的是空格 → **不 intercept**，把键放回页面（用户要翻页）；
其余键照常作用在同一个视频上。

⚠️ 判的位置不能往前挪：往前挪会把整个视频连同其它键一起放掉，
那就退回到「什么都不接管」了 —— 而那正是我们要避免的。
⚠️ 放行时 `holdOwner` 必须清成 `null`：长按空格时浏览器会持续派发
`repeat` 事件，而 repeat 分支要求 `holdOwner === action` 才拦。
不清的话，长按空格页面就滚不动了 —— 那是「让路让一半」。

#### 查视频要缓存

「查视频」的结果按 **DOM 变更代次**缓存（`generation`）：
MutationObserver 只推进代次、不重建列表，静态页面上代次长期不变 → 一直命中。
**null 结果也缓存**（页面上没有视频是最常见的情况）。
非 null 的结果额外有 5 秒 TTL（分数里含随时间变化的成分：键盘目标的 30 秒窗口、
「用户选过」的 10/60 秒窗口）。

命中缓存前必须**重新确认目标还挂在文档里** —— 因为 shadow tree 的增删
**不会**推进 document 级代次，只有这条能认出「它已经被摘掉了」。

#### 缓存必须跟着 body 换人

`null` 结果**没有 TTL** —— 「页面上没有视频」是最常见的情况，
而它必须一直有效到 DOM 真的变了为止。于是「DOM 变更代次」停摆 = 快捷键永远醒不过来。

代次停摆的**真实形状**：站点 `document.body.replaceWith(newBody)`（SPA 重建页面）。
MutationObserver 绑的是**元素** —— 观察者还挂在**已经脱离文档的旧 body** 上，
而旧 body 再也不会变化。实测（真实 Chromium）：

| 场景 | 快捷键路径的倍速 |
| --- | --- |
| body 没被换掉（只 `innerHTML = ''`） | 1.1（正常） |
| body 被替换 | **1（冻结）** |
| 替换之后用户点了一下视频 | 1.1（自愈） |

⚠️ 症状之所以自相矛盾（「图标能点、快捷键没反应」）：工具栏那条路按帧重算，
不吃这份缓存。
⚠️ 「点一下就好了」这个自愈路径来自**用户手势**顺带触发的一次作废 ——
极难让人联想到「body 被换掉了」。

所以观察必须**跟着 body 换人**：见 `BodyObserver` 一节。

#### 测量结果按帧复用，但候选列表不缓存

上面那条缓存的是**判定结果**。再往下一层，「量」本身也很贵：
`getBoundingClientRect()` 会**强制排版** —— 它是整条候选路径里最贵的一次调用
（实测采样里它的占比比 `querySelectorAll` 还高）。

所以测量结果（矩形 + 计算样式）**按帧复用**：

- 同一帧内布局不会变（滚动与 CSS 动画都会推进帧号）；
- 跨帧必须重测 —— 视频可能刚被站点挪了位置；
- DOM 变了（改 class、改 style）立刻作废（按代次失效）。

⚠️ **候选列表本身不能缓存**：DOM 的增删是**同步可见**的
（同一个同步块里 `appendChild` 之后立刻查询，答案必须包含新来的那个），
而 MutationObserver 的失效通知是**微任务** —— 缓存列表会漏掉它。
这一条有专门的回归守卫（「视频被摘掉后必须立刻查不到」）。

#### 按住不放的重复按键不重扫

浏览器在用户**按住**某个键期间会持续派发 `keydown`（`event.repeat === true`）。
那些事件不带来任何新信息：还是同一个键、还是同一次手势。

但注册表记手势的那条路（`handleGesture`）本来每次都要**重扫整页**，
而一次按键里它要走两遍（键盘控制器找接管目标 + 注册表记手势）。

所以 `event.repeat` 的重复事件**不记手势**：不刷新时间戳，也不重扫。
「按住」恰恰是持续时间最长的手势（长按空格翻页、长按方向键快进），
实测按住一秒就是 30 次全页扫描。

⚠️ 副作用是刻意的：时间戳不再被重复事件刷新，于是「用户按住键的同时，
站点把自己的预览视频播起来」不再被算成「用户按了播放」—— 那本来就更像
站点在抢用户的意图。

### `BodyObserver`

文件：`src/content/bodyObserver.ts`

职责：**一个**地方回答「`document.body` 是不是被换成了另一个元素」。

MutationObserver 绑的是**元素**，不是文档。站点把 body 整个换掉之后，
观察者就成了孤儿 —— 它还挂在已经脱离文档的旧 body 上，而旧 body 再也不会变化。
这个坑有三处都在踩（注册表的 DOM 代次、调速胶囊的角标目标、首次引导的全屏状态），
所以抽成一处。

两个观察器，各管一段：

| 观察器 | 看什么 | 回调 |
| --- | --- | --- |
| body 级 | body 内部的一切变化（`subtree` 覆盖所有后代） | `onBodyMutation` |
| `<html>` 级 | documentElement 的**直接子节点** | `onHostMutation` |

`<html>` 级观察器唯一的职责是**发现 body 换人了**：换掉之后把 body 级观察器
重新挂到新 body 上，并通知 `onBodyReplaced`（订阅方据此作废缓存）。

⚠️ 为什么 `<html>` 级只看**直接子节点**、且这些记录**不**转发给 body 回调：

我们自己的浮层（控制条、网页全屏背板、调速胶囊、提示卡）全都挂在 **`<html>`** 上
（见 `viewportRoot` 一节）。若去观察 documentElement 的**子树**，
我们自己挂/摘浮层就会被算成「DOM 变化」—— 注册表的变更代次每次浮层显隐都前进一次，
「测量结果按帧复用」那套优化就被打回原形（每次按键都要全页重扫）。

⚠️ `onHostMutation` 另有一个用途（目前**还没有订阅方**）：
「我们的浮层被站点整片抹掉了，要重建」—— 浮层挂在 `<html>` 上，
站点摘掉它们时这一层会收到通知。
⚠️ 但「站点把 **`<html>` 本身**换掉」不在本工具的覆盖范围内：
本工具观察的是 documentElement，它一旦被换掉，观察者就成了孤儿
（与 body 被换掉一模一样的病，只是高了一层）。那一档要观察的是 **document**，
建议单独修。

### `FullscreenController` + `FullscreenControls`

文件：`src/content/fullscreenController.ts`、`src/content/fullscreenControls.ts`

职责：

- 管理网页全屏 overlay 生命周期；优先 reparent，失败退回 CSS cover
- 退出时还原原父节点、内联样式、controls、body overflow
- 还原前校验 `originalNextSibling` 仍是原父节点的孩子，否则 append 兜底
  （全屏期间页面重排 DOM 移走 sibling 时，避免 NotFoundError 卡死全屏）
- 节点被页面丢弃时只清理、不重插（health check 每 500ms）
- 控制条：播放/暂停、进度、时间、音量、倍速（可点选档位）、退出；鼠标静止 3 秒隐藏
- reparent 模式下由控制条接管视频表面的左键点击（单击 = 切换播放/暂停）
- 控制条**住在自己的 shadow root 里**（见下文「为什么控制条要 shadow DOM」）

**为什么控制条要 shadow DOM**：我们把 UI 注入到**任意站点**的 DOM 里，站点的
全局 CSS 会顺着继承和元素选择器把控制条彻底摧毁。实测一个「有自己的设计系统」的站点：

```css
* { box-sizing: border-box !important; }
div { font-family: "Comic Sans MS", cursive !important; line-height: 3 !important; }
button { all: unset !important; }
input[type="range"] { -webkit-appearance: none !important; height: 40px !important; background: red !important; }
```

结果是控制条变成一整条红色大块、按钮塌成 22×48、时间显示成 Comic Sans、进度条完全不可用。

试过的其它办法都不行：
- 显式重声明每个属性：挡不住站点的 `!important`（作者 `!important` 优先级高于普通作者声明）。
- `all: revert`：revert 只回退到**上一层**样式，站点自己的 `!important` 依然生效。
- `all: initial`：更糟，连 `position: fixed` 都会被重置。

shadow root 是一条**结构性**的隔离边界：页面样式进不来，我们自己的样式也出不去。
代价是外部代码要用 `root.shadowRoot.querySelector(...)` 才能拿到内部元素，
控制条的样式也不能再靠页面里的 `<style>` 生效 —— 所以那份样式必须自给自足
（`src/content/controlsStyles.ts`）。

⚠️ 页面级提示（调速胶囊、常驻角标、接管提示、首次引导）**还没有**这道边界 ——
它们挂在 `document.body` 下的 light DOM，站点一条 `div { ... !important }`
就能把它们打穿（角标对比度实测从 11.21:1 掉到 2.29:1）。
这是「同一个问题、控制条已修而页面级提示漏网」的现状。

#### 控制条的几条硬约束

这一轮的实测把几条「看起来是审美、其实是功能」的约束钉死了：

| 约束 | 原因 |
|---|---|
| 换播放/静音图标**不能碰 `innerHTML`** | 换掉光标下的元素会让浏览器在**光标不动**的情况下重新派发 `mouseenter` → `cancelHide()` 取消隐藏计时器 → 控制条从此永不隐藏。改法：两个 SVG 叠放 + class 切换 |
| 指针移入控制条要**重新计时**（`scheduleHide`）而不是取消计时 | 同上 |
| 滑块的 `change` 事件要分得出是不是键盘驱动 | `change` 分不出来源，无条件 `releaseFocusToPage()` 会让滑块每按一次键就丢焦点 → 长按方向键无效 |
| 进度条步长 = **5 秒**（对齐 `SEEK_STEP_SECONDS`），PageUp/PageDown = **固定 30 秒** | 原生 range 的 `step` 默认取 `max/100`；原生 PageUp 是「范围的 10%」—— 10 秒视频跳 1 秒（无感）、2 小时视频跳 12 分钟（离谱） |
| 时间标签与倍速徽标要**固定宽度** | 内容宽度变化会把进度条挤得忽宽忽窄，控制条横向抖动 |
| **断点必须来自实测值，不能来自估算** | 断点原先是估的（500 / 380），而真实需求是 553 / 401 —— 于是有**两段**视口宽度（501–546px、381–400px）里**退出按钮被推出屏幕**。390px（iPhone 12/13/14）正落在第二段：手机上鼠标点不到退出按钮，用户被关在全屏里。现在实测需求与断点都收在 `src/content/controlBarLayout.ts` 这一个真源里，CSS、JS、e2e 三方都从它取（各写一份就会漂，而漂了**没有任何测试会红**） |
| 收起态的**退出入口不能消失** | 控制条 3 秒就整个消失 —— 「我正在扩展的网页全屏里」这个状态没有任何常驻表达，退出入口也跟着消失。现在收起时留一枚 28×28 的独立退出钮（同一 shadow root、同一角、常态半透明），任何活动即恢复完整控制条 |
| 未填充轨道的对比度要对着**明亮画面**算，不是对着遮罩算 | 半透明白轨道与白色画面只有 2.09:1（实测），低于 WCAG 1.4.11 的 3:1 |
| 窄屏（≤640px）要换布局 | 固定宽度 flex 在 390px 下 `scrollWidth` 490 → 倍速与退出按钮出屏，**鼠标用户没法退出全屏** |

⚠️ 窄屏那条**不能**用 `.bar { overflow-x: auto }` 兜底：
`overflow-y: visible` 在 `overflow-x` 不是 `visible` 时会被规范算成 `auto`，
控制条于是变成纵向滚动容器，**倍速菜单（绝对定位在按钮上方）会被整个裁掉** ——
用一个问题换另一个。正解是让内容真的塞得下（实测 320px 宽下这套刚好放得下）。

进度条的跳转「钉住」有一个上限（`SEEK_PIN_TIMEOUT`，3 秒）。提交 seek 后播放器
会有一小段时间继续报旧的 `currentTime`，照它渲染会把滑块拽回原位（回弹），所以
`pendingSeek` 期间滑块钉在目标位；但 `seeked` **不一定来**——请求浏览器无法寻址的
位置时 Chrome 会拒绝跳转且不派发该事件。只靠 `seeked` 解除钉住，滑块会永久冻结在
一个假的进度上，比回弹更糟：用户以为跳转成功了。所以钉住必须有上限。

### 接管失败时的反馈

`KeyboardController` 在吞键前先问 `canEnter()`：视频必须与内容脚本在**同一个
document**（`video.ownerDocument === document`）。进不去就不吞键、放行给页面——
但**放行必须配一句解释**，否则在用户眼里「不吞键」和「扩展坏了」是同一件事。
所以同一分支里调 `notifyTakeoverUnavailable()`，由 `TakeoverNotice` 弹一条
2.6 秒的提示。

> ⚠️ 6.1.0 之前「跨 document 的视频」= 同源 iframe 里的视频，那必然接不了。
> 现在内容脚本注入到所有 frame，iframe 里**也有一份**内容脚本，
> 那份脚本看到的 `document` 就是 iframe 自己的 document —— 于是
> `canEnter` 对 iframe 里的视频**成立**，「跨 document 接不了」这条老限制
> 在 iframe 场景下**已经消失**（实测：iframe 里的视频按 `f` 能进全屏）。

提示刻意**不说原因**：从扩展这一侧无法可靠区分 DRM 受保护、跨 document、无宿主
这几种失败，猜一个具体原因比不说更糟。它只解释「不会发生什么」。

### 首次使用引导

`FirstRunHint` 是这个产品里唯一一处「主动出现」的界面，因此边界收得很紧：

- 只在该扩展**从未展示过**时触发（`storage.local` 的
  `vsc-first-run-hint-shown`，设备级状态，不占 sync 配额、不跨设备同步）
- 等到 `play` 之后**再过 2.5 秒**才出现：自动播放的广告位与悬停预览都会派发
  `play`，只按 `play` 就弹提示等于打扰
- 「用户还在看」靠真实的 `pause` / `ended` **事件**判定，不去轮询 `video.paused`：
  要回答的是「这段时间里有没有停下来」，事件是唯一诚实的信号
- 文案用**用户当前真实的绑定**渲染（改过键之后不能教一个错的键），且不含
  播放/暂停——用户刚按过它
- 任何按键/点击立即消失；12 秒后自行淡出；展示不出来（无可挂载宿主）就不写
  标记，用户之后仍有机会看到

#### 引导住在那份文档里，就得放得下那份文档

6.1.0 之后引导住在「拥有视频的那个 frame」里，而那个 frame 的视口可能小得离谱
（嵌入框常常只有 320×180）。于是有了「**放得下的那一版**」这条契约：

- 完整版四行，在 320×180 的框里**盖住播放器 72%**（实测，真实 Chromium）；
  在 240×135 的框里**装不下**（顶部被裁，top = -11px）。
- 所以引导会**量一量**：完整版放得下（高度 ≤ 视口的一半）就放完整版，
  放不下就退到**精简版**（只留「按哪个键」那两行 —— 那是引导存在的理由）。
- ⚠️ 判据是**高度占视口的比例**，不是「放不放得下」：「放得下」太弱 ——
  130px 的提示塞进 180px 的框里放得下，却把整个播放器糊住了。
  一块贴片最多占这个 frame 的一半。
- ⚠️ 舍弃的只是**视觉**版面，不是信息：读屏播报走的仍是完整版
  （live region 不占版面）。

⚠️ 那份「量」必须在节点**已存在但透明**时做 —— 所以提示的骨架拆成了
`prepare()`（建好节点、写好文本，返回可测量的节点）与 `present()`（显形 + 播报）两步
（见 `TransientPill`）。

#### 唯一一次机会，不能被看不见的视频烧掉

这个提示是**用户这辈子唯一一次**的主动教学机会。6.0.9 的落盘判据是
「弹出来就写 flag」，于是长文页上任何一个**看不见**的自动播放视频
（`display:none`、零尺寸、在视口外）都能把这唯一一次机会烧掉 ——
用户从此再也不会知道这个扩展会做什么。

现在有三道闸门：

1. **三重可见性判据**（`isVisibleToUser`）：`getClientRects().length > 0`
   （排除 `display:none`）+ `getBoundingClientRect()` 宽高 > 0 + 与视口相交。
2. **读完才落盘**：提示出现后还要有一段阅读窗口（中途没被打断、页面在前台）
   才写 flag。刷新会打断阅读窗口 —— 用户还没来得及读，那唯一一次机会
   **不该**被消耗掉。
3. **失败兜底**：连续 3 次「弹出来被打断」之后不再打扰，但**绝不写**一次性 flag
   （机会还在，只是别再来烦他）。

另有一处 `IntersectionObserver`：窗口期里视频不可见时**不放弃**，
等用户滚过去、它变可见时再补上这一次提示 ——
否则会留下「用户滚过去就再也看不到」的洞。

`TransientPill` 是 `SpeedToast`（速率胶囊）之外两处一次性提示的共用骨架
（建节点 / 判空宿主 / 自愈 / 计时 / 清理），文案与停留时长由调用方给。

### 页面级提示的一套视觉语言

页面上有**五块**我们自己的浮层：调速胶囊、接管提示、首次引导、常驻角标、扩展已更新提示。
它们以前各写各的样式 —— 于是同一个产品里出现了两种字号、两种圆角、
两种淡入时长，用户只会读成「这是两个东西」。

现在按**类别**分，不按**功能**分：

| 类别 | 谁在里面 | 形状 | 说明 |
| --- | --- | --- | --- |
| 胶囊 | 调速胶囊、接管提示 | 药丸 | 同一类东西：**锚在视频上、一次性、只说「刚刚发生了什么」**。两者必须**一模一样** |
| 卡片 | 首次引导 | 圆角矩形（自己的底色） | 另一类东西：用户要**读**它、有关闭按钮。形状保留「卡片」身份，但**嗓子**与胶囊相同 |
| 角标 | 常驻倍速角标 | 自己的 | 常驻物，与一次性提示不是一回事 —— 尺寸**不参与**这套 token |
| 状态通知 | 扩展已更新提示 | 自己的 | 系统消息：它**站着不走**（只能靠刷新页面消失），所以不能做成胶囊（胶囊 1 秒后就淡出，用户会以为它也会消失），也不做成卡片（卡片带关闭按钮，而系统消息没有「关闭」这个选项）。嗓子与胶囊/卡片相同 |

「嗓子」= 字号 / 字重 / 行高 / 字体族；「形状」= 圆角 / 底色 / 内边距 / 淡入时长。
卡片与胶囊**只共享嗓子**，形状各走各的 —— 形状相同就分不出哪个是要读的。

三套 token 住在 `src/content/runtimeStyles.ts`：

- `NOTICE_PILL_TOKENS` —— 胶囊（含接管提示）
- `NOTICE_CARD_TOKENS` —— 卡片（首次引导）
- `NOTICE_STALE_TOKENS` —— 状态通知（扩展已更新提示）

⚠️ 派生量必须**跟着 token 走**，不能各写各的数：`NOTICE_ROW_HEIGHT`、
`NOTICE_MAX_HEIGHT` 都是从胶囊 token 推出来的（`runtimeStyles.test.ts` 里有
一条用例专门按 token 重算它们）—— token 改一次而常量没改，
接管提示就会爬回胶囊那一行去压住它。

#### 层级（z-index）是一条阶梯，不是一堆 2147483647

以前五块浮层**加上** live region 全都写在 `2147483647`（32 位有符号整数的上限）。
同层意味着彼此可能互相盖住（谁后插入谁在上面），而「提示盖住提示」
用户只会被解读成「这个扩展坏了」。

现在从下到上是一条**严格递增**的阶梯（`runtimeStyles.ts`）：

```
全屏背板 < 舞台 = 视频 < 字幕 < 控制条 < 页面级提示 < live region
```

- live region **必须最高**：它是产品唯一对读屏用户可用的反馈通道，
  被别的层盖住等于对读屏用户不存在。
- 页面级提示高于控制条：全屏时两者会同时出现，控制条在画面下沿、
  提示锚在视频边角，提示压住控制条会挡住退出按钮。
- 同时还有一条**底线**：任何一层都不得低于 2147483000 ——
  有人把某个常量改成 1，页面级提示就会被站点的内容整个盖住
  （而「顺序」那条断言在只有一层掉下去时仍然是绿的）。

守卫断言的是**相对顺序**（`A < B < C`），不是魔法数字；
但底线那条是**绝对值**，两者缺一不可。

### 点击语义的所有权

reparent 把 `<video>` 搬进我们自己的 overlay，视频就脱离了站点播放器的祖先链
（YouTube 的 `#movie_player`、B 站的播放器容器）。站点那些「点击视频切换播放」的
监听器挂在祖先上、靠冒泡收事件，祖先链一断它们就再也收不到点击——实测 YouTube
网页全屏里左键点击毫无反应，而空格正常，因为键盘走的是我们自己的
`document_start` 捕获通道。

所以**接管表面就要接管点击语义**：`FullscreenControls` 在 reparent 模式下给视频
自己挂 `click`，只认左键、且 `defaultPrevented` 时让位给站点。

css-cover 模式必须相反：视频留在站点 DOM 原位，站点监听器照常工作，我们再切一次
就是双重切换（点一下 = 暂停又播放 = 看起来仍然没反应）。因此所有权判定是
`ownsVideoSurface()` 这个**函数**而不是常量——180ms 探测可能把模式从 reparent
动态降级到 css-cover，`unmount()` 也必须摘掉监听器，否则退出全屏后残留监听器
会和站点自己的处理器双重切换。

双击不需要去抖：浏览器在一次双击里派发两个 `click`（`detail=1` 与 `detail=2`），
两次切换互相抵消、播放状态净变化为零，与 YouTube 原生双击的表现一致（实测原生
双击后 `paused` 不变、只进全屏）。

### 180ms 健康探测：「媒体丢了」只能看 `readyState`

进全屏 180ms 后会探一次「站点有没有把媒体弄丢」，真丢了就降级到 css-cover
（视频回页面原位、字幕保持可见，代价是全屏没那么干净）。

判据必须是 **`readyState` 从有到无**（`state.readyState > 0 && video.readyState === 0`），
**绝不能是 `paused`**。实测三条对照（真实 Chromium）：

| 动作 | 派发的媒体事件 | `readyState` | `currentTime` |
|---|---|---|---|
| 用户暂停 | 只有 `pause` | 保持 4 | 不变 |
| reparent（搬节点） | **一个都没有** | 保持 4 | 不变 |
| 站点 `load()` 重载 | `abort`→`emptied`→`loadstart` | **→ 0** | → 0 |

也就是说暂停和搬节点都不改变 `readyState`，只有真的丢媒体才会掉到 0。
旧判据是「进全屏时在播、现在不在播」，用户按一下暂停就命中 —— 而 180ms
正好覆盖「刚进全屏、还在找按钮」的那一瞬，按空格或点画面暂停是进全屏后
最常见的第一个动作。后果是视频在满屏画面刚出来时被悄悄拽回页面原位。

`> 0` 这个前提同样不可省：页面本来没挂源的占位 `<video>` `readyState` 恒为 0，
不加前提会把它们全部误判成故障。

配套：`restoreIfLost` 里的「用户主动暂停过就不再自动播」豁免也必须去掉。
`userPaused` 一旦置真永不复位，用户「暂停 → 继续播 → 退出全屏」时退出补偿
会被永久跳过，视频卡在暂停。而三个调用点都是「拍快照 → 同步搬节点 → 立刻补偿」，
中间没有插手的空隙 —— reparent 本身也不会暂停视频，真出现 paused 翻转
就是站点动了媒体，那正是该恢复的时候。

### `SpeedToast`

文件：`src/content/speedToast.ts`

职责：

- 全屏内外调速时都在视频角落淡入 `1.5x` 小胶囊，约 1 秒后淡出
- **胶囊淡出不等于消失**：若视频仍在播放、仍在视口里、且用户没有再操作，
  它会缩成一枚很淡的小角标常驻在视频角落，直到视频暂停 / 滚出视口 / 进入全屏
- 控制条 3 秒无操作即隐藏，不能指望它承担键盘调速的反馈
- 有自己的节点与跟随滚动/缩放的定位（与 `TransientPill` 的差别在此：
  这条提示活得更久，位置要跟着视频走）

**为什么常驻角标值得做**：控制条 3 秒就隐藏，键盘调速时它根本不在屏幕上，
而非全屏状态下**没有任何其它地方**显示当前倍速。胶囊一消失，用户就只能凭记忆
猜自己刚才调到了几倍。角标是「随时可见当前倍速」与「不打扰」之间的折中：
它很淡、不可点击、且有明确的三条退场条件（暂停 / 滚出视口 / 进全屏）。

⚠️ 进全屏时角标**不出现** —— 控制条上就写着倍速，再挂一个角标是重复信息。
这条判定同时绕开了一个死角：控制条自带的退出按钮走 `FullscreenController.exit()`，
不经过运行时，角标拿不到「该撤下了」的通知；干脆不让它在全屏里出现。

### 帧的归属：快捷键该作用在哪个视频上

**这是扩展里最容易被忽略、也最影响日常使用的一条边界。**

实测（真实 Chromium）两条硬事实：

1. **键盘事件只会被派发到焦点所在的那个文档。** 焦点在顶层文档 → 只有顶层文档
   收到 `keydown`；焦点在 iframe 里 → **只有那个 iframe 收到**，顶层文档一个都收不到。
2. **焦点在 iframe 里时，顶层文档的 `document.activeElement` 是那个 `<iframe>` 元素**
   （焦点代理），而那个 iframe 自己的 `document.hasFocus()` 为 true。

第 1 条决定了内容脚本**必须注入到所有 frame**（manifest 的 `all_frames: true`）。
只注入顶层时，「用户点了播放键 → 焦点进了播放器 → 然后按 `=`」这条最常见的路径
完全无效 —— 页面越依赖 iframe 嵌入播放器（视频站、网课、新闻站），扩展越像没装。

第 2 条决定了**顶层 frame 不许上报焦点**：点 iframe 里的东西时，顶层文档也会收到
`focusin`（焦点代理），两边都上报的话，后到的那个赢，于是 background 记住的是
顶层 frame —— 又回到「图标点了没反应」的老问题。判据在 `src/content/frameScope.ts`：

```ts
ownsUserFocus(doc)  // doc.hasFocus() && activeElement 不是 iframe/frame 元素
```

⚠️ 判 iframe 用 `tagName` 而不是 `instanceof`：`instanceof` 跨 realm 恒为 false
（内容脚本与页面是两个 realm，iframe 元素来自另一个 realm）。

#### 「点扩展图标」为什么只发给一个 frame

内容脚本注入到所有 frame 之后，同一个「点扩展图标」的意图会**同时**送到页面里的
每一个 frame —— 全都执行就是进好几次全屏、弹好几个提示。

浏览器只把焦点给一个 frame，所以「用户正在看的画面」就在那一个 frame 里：

- 内容脚本在拿到焦点时上报一次（`window.focus` / `focusin` / `pointerdown`，
  150ms 限流，免得连续移动焦点把 service worker 唤醒得太频繁）；
- background 记下 `sender.frameId`（`tabId → frameId`）；
- 点图标时 `chrome.tabs.sendMessage(tabId, msg, { frameId })` **只发给它**。

⚠️ **不靠 `document.hasFocus()` 当场判**：点工具栏图标的那一刻，焦点在
**浏览器界面**上，页面多半是失焦的 —— 靠 `hasFocus` 判，结果是「图标点了没反应」。

⚠️ **必须落一份 `storage.session`**：service worker 空闲约 30 秒就被浏览器回收。
「在 iframe 里的播放器上点了播放 → 看了半分钟 → 才去点扩展图标」是很常见的节奏 ——
那时内存 Map 已经空了，图标会被发给顶层 frame，而顶层 frame 里根本没有视频，
于是用户看到「此页面没有视频」：明明屏幕中央就是视频。

⚠️ **frameId 不是连号的**（实测：顶层是 0，同源 iframe 是 2，1 号不存在）。
这是 Chrome 的实现细节，不许写死。

⚠️ **记下的 frame 可能已经没了**（页面重载、SPA 把 iframe 换掉）。这时退回顶层
frame 再试一次 —— 图标点了却毫无反应是最糟的体验。退路**不按错误文案分流**
（Chrome 在不同版本下给的是不同的字符串），多试一次的代价只是一次失败的回调。

#### 每个 frame 各自跑一份运行时，谁不许说话

| 行为 | 规则 | 理由 |
| --- | --- | --- |
| 调速、播放控制等**快捷键** | 只有焦点所在的那个 frame 执行 | 键事件本来就只到得了那一个 frame |
| 首次引导 `FirstRunHint` | **视频所在的那个 frame** 弹（同一标签页只弹一个） | 每个 frame 只收自己 document 里的视频 —— 引导只跑在顶层，就等于「页面里唯一的视频在嵌入框里时，引导永远不出现」 |
| 倍速上报 `reportSpeed` | **焦点所在的那个 frame** 上报（判据是 `ownsUserFocus()`，不是「我是不是顶层」） | 顶层在焦点落进 iframe 时要让出发言权，否则工具栏标题显示的是某个 iframe 里的倍速 |
| 页面级提示（胶囊、接管提示） | 跟随视频所在的那个 frame | 提示住在**自己那份文档**里，坐标换算到**那份文档**的视口坐标系（见 `frameOffset`） |

⚠️ 全局唯一的例外是「接管提示」：iframe 里的视频**可以**被接管（`all_frames` 之后
它就在自己的 document 里），这是 6.1.0 相对 6.0.9 最大的能力变化。

#### 「这个标签页的视频在哪儿」：background 问一圈

6.1.0 之后每个 frame 只管**自己 document 里**的视频（注册表不再钻进 iframe ——
两个运行时抢同一个 `<video>` 会打架）。于是「这个标签页的视频在哪儿」这件事
**只有问一圈才知道**：background 自己看不见任何 DOM。

协议三条消息（`src/shared/types.ts`）：

```
background ──vsc-video-owner-ask──▶  这个标签页的每一个 frame（广播）
frame      ──vsc-video-owner-report─▶  background（回答：explicit / watched / playing）
content    ──vsc-video-owner-query──▶  background（「别的 frame 有吗？」）
```

两个信号（`explicit` / `watched`）是因为两条路径的契约不同：
显式操作（点图标）用 `getCurrentVideo()`，快捷键用 `getWatchedTarget()` ——
后者更严（页面里可能有个小预告视频能接管，却不是用户正在看的那个）。

⚠️ **回答必须走 `chrome.runtime.sendMessage`，不能走 `tabs.sendMessage` 的响应**：
一次广播会有好几个 frame 同时回答，而 `tabs.sendMessage` 只保留**一个**响应，
其余的回答会被丢掉。background 从 `sender.frameId` 认出是谁回答的。

两个用途：

1. **点图标时把点击送到对的那个 frame**。实测（真实 Chromium）：页面上唯一的视频
   在嵌入框里、焦点在顶层时，点图标得到的是「这个页面里没有视频」—— 而屏幕中央
   明明就是那个视频。优先级是「焦点所在的那个 → 正在播的那个 → 随便一个有视频的」，
   焦点仍然优先（「用户在哪儿操作就动哪儿的视频」不能破）。
2. **快捷键没有目标时说出真相**。快捷键在没有明确目标时必须**放行**给页面
   （键属于页面，不接管错对象），但放行之后如果什么都不说，用户看到的就是
   「按了没反应」—— 能得出的唯一结论是「扩展坏了」。于是这一层没有视频时，
   扩展去问一圈，有就告诉用户「视频在嵌入框里 —— 点一下它就能用快捷键」。

⚠️ 快捷键**不会**去抢别的 frame 的视频：抢了就破坏了「焦点决定作用对象」。
提示只负责**说出真相**，动谁由用户决定。

⚠️ 广播要**限时**（120ms）：首选 frame 自己回答「我有视频」时立刻返回（这一路实测
约 5ms），只有「首选 frame 里没有视频」时才会等到超时 —— 多等 120ms 换
「图标点得中」是划算的。再长就是用户直接感知的延迟了。

#### 广播是**一发**的：没就绪的那一层永远答不上来

`chrome.tabs.sendMessage` **不会重播**。某个 frame 当时还没注册好监听器，
它就永远收不到这一次的提问。

而内容脚本是 `document_start` 时**动态 import** 的（见 `content-loader.js`：
它同步注册按键桥接，然后 `import(chrome.runtime.getURL('content.js'))`），
所以页面刚打开的那几十毫秒里，某一层完全可能还没就绪。

于是「零份回答」有两种可能，从外面看**一模一样**：

- 「这个页面真的没有视频」；
- 「那个 frame 的内容脚本还没准备好」—— 页面刚打开的那一刻最常见。

但它们对用户是天壤之别：前者该沉默，后者该说「视频在嵌入框里」。
**页面刚打开就按 `f` 却毫无反应**，是最容易被当成「扩展坏了」的时刻。

四处配合，缺一不可：

| 位置 | 做法 | 为什么 |
| --- | --- | --- |
| 内容脚本 | **先注册消息监听器**，再 `await loadSettings()` | 设置还没加载完，不影响回答「我手上有视频」 |
| 内容脚本 | 回答**推迟一个微任务** | 注册表的候选列表按 DOM 变更失效，而失效通知（MutationObserver）**也是微任务** —— 同步的查询会看到过期的答案（实测 `explicit` 报成 false） |
| background | **没人回答就再问一遍**（多等 80ms） | 多一次广播的代价只是一次跨进程往返，换来的是「页面刚打开时按快捷键也有反馈」 |
| background | 「没有主人」**不消耗**提示的冷却期 | 只有真的找到主人，才说明那句话成立；一次查不到就把 60 秒的冷却打掉，用户会在整整一分钟里得不到该得的提示 |

⚠️ 两条节流阀要**分开**：向 background 的**查询**按 2 秒节流（省掉无谓的跨进程
往返），给用户的**提示**按 60 秒节流（别刷屏）。原先只有一个阀，调哪一头都会
顾此失彼。

### 读数作废：那个报出倍速的 frame 没了怎么办

工具栏标题是「这个标签页此刻的倍速」这唯一的常驻读数，而 background 自己
看不见任何 DOM —— 它只**记得**「这个倍速是哪个 frame 报的」（`storage.session`
里的 `vsc-tab-rate:{tabId}` = `{ rate, frameId }`）。

于是有一条必须回答的问题：**那个 frame 还在吗？**

以前唯一的判据是「**报出这个倍速的就是这个 frame 自己**，而它现在说它没有
受控视频了」。判据本身是对的，但它有个死穴：那个 frame 没了之后
**没有人会再来说这件事** —— 它已经不会说话了。

实测（真实 Chromium）：视频在 iframe 里、调到 1.2 倍 → 标题是
「Video Speed Controller — 1.2x」；SPA 把那个 iframe 整个换掉
（`slot.innerHTML = ''`）→ 页面上一个视频都没有了，标题却还挂着 1.2 倍，
`storage.session` 里那份记录也一直指着那个已经不存在的 frame。点击页面也没用
（顶层 frame 报「我这儿没有视频」是**正常**的 —— 视频可能在别的 frame 里）。

两条独立的作废路径（哪条先到算哪条）：

```
content    ──vsc-frame-gone──▶  background（「我这一层要走了」：pagehide）
content    ──vsc-speed-report─▶  background（「这一层没有受控视频」：**不带 rate**）
background ──vsc-frame-probe─▶  某一个 frame（「那个视频还在吗？」）
```

| 位置 | 做法 | 为什么 |
| --- | --- | --- |
| 内容脚本 | 卸载前（`pagehide`）说一句「我走了」 | 这是**唯一确定**的信号：报出这个倍速的那个 frame 自己说它要走了。⚠️ `persisted = true`（进后退缓存）时**不能说** —— 页面还可能原样回来 |
| 内容脚本 | 记住「我报出去的是**哪个**视频」 | 判「那个视频还在不在」要问的是**那一个**视频，不是「这一层此刻有没有视频」：视频被滚出视口、被 `display:none` 藏起来时，后者会说「没有」，而那个视频其实还在、还在按 1.2 倍播 |
| 内容脚本 | **盯着**那个视频（body 子树观察者） | 视频被站点从 DOM 里摘走时**没有任何事件**会通知扩展：没有 `ratechange`（它只是被删了），也没有 focus 事件。没有观察者，「这一层没有受控视频」这句话就**永远发不出去**，background 收到的最后一个信号永远是「1.2 倍」 |
| background | 「这一层没有受控视频」（不带 rate）**不是无效消息** | 它**不**等于「这个标签页没有倍速」：倍速可能是**别的** frame 报的（视频在嵌入框里、这一层是顶层）。⚠️ 以前这里直接 `return` 把它整个丢掉 —— 那条信号**永远到不了**，标题就一直挂着早已不存在的倍速 |
| background | URL 变了 → 探针问一句「那个视频还在吗」 | 换页是**时机**，不是判据。⚠️ `changeInfo.url` 出现**不代表**导航真的发生（`history.pushState` 也会带它），而那时视频还好好地播着 —— 清掉就是让标题与画面自相矛盾（6.2.0 修过一次的老毛病） |
| background | 探针**不按错误文案分流** | Chrome 在不同版本下给的是不同的字符串（「No frame with id 3 in tab with id 7」/「Frame with ID 3 was removed」…）。只认「有没有人回答」：回答了 = 还活着；没人回答 = 已经不在了（扑空时重试一次：内容脚本是 `document_start` 动态 import 的，frame 在了、监听器还没注册上的那几十毫秒里会扑空） |
| background | 探针是**异步**的 → 复位前要核对记录没变 | 整页导航之后新页面的内容脚本会重新上报 —— 那份新读数必须赢过「按旧判据清掉」这个动作（`tabRateRevisions` 就是干这个的版本号） |

⚠️ 复位时是**删掉**那份记录，不是写成 1：那份记录的价值全在「是谁报的」上，
写成 1 只会留下一条「这个标签页是 1 倍」的假记录。

⚠️ **跨文档导航时 Chrome 自己会把这一标签页的标题恢复成默认值**
（实测：探针里全程没有一次 `setTitle` 调用，标题却已经回到默认态）。
所以「整页导航后标题复位」有两条独立的保障：Chrome 自己那一条，
以及我们自己的那一条 —— 后者管的是**同文档**里发生的事（SPA 换页、
站点把视频换掉），那两条 Chrome 管不着。

### 嵌入框里的网页全屏：撑大装着播放器的那一整块

文件：`src/content/iframeExpansion.ts`

VSC 的网页全屏是**自绘覆盖层**（不是原生 fullscreen）：视频被搬进
`#vsc-page-fullscreen-overlay`（`position: fixed; inset: 0`），画面按
100vw/100vh 铺开。这两样的参照系都是「**当前文档的视口**」。

于是视频在 iframe 里时，覆盖层铺满的是 **iframe 自己那块视口**
（真实 Chromium 实测：overlayRect 320×220 === innerViewport 320×220，
而 topViewport 是 1280×720）—— 用户点了「网页全屏」却只在那块小框里全屏，
顶层页面原样不动，「网页全屏」名不副实。

**修法**：让**父文档**把「装着这个视频的那个 `<iframe>` 元素」撑满自己的视口。
iframe 内部的覆盖层是 fixed + inset: 0（相对 iframe 自己的视口），
视频是 100vw/100vh（vw/vh 同样相对 iframe 自己的视口）——
iframe 元素一旦铺满顶层视口，里头的覆盖层与画面自然就铺满整个页面。
连站点自己写的 iframe 尺寸样式都不用管（用 `!important` 压过去）。

三条约束：

- **每一跳只发给 `window.parent`**，从来不跨级去动 `window.top` 里的元素。
  中间层自己也在 iframe 里时，它撑大子 frame 之后会**再向上一级**请求一次
  （链式），于是最外层的 iframe 也被撑开 —— 但每一层只认领**自己文档里**的
  那个 iframe 元素。
- **消息体不带「我要你撑大哪个 iframe」**。那种写法等于让页面可以自报家门、
  指名道姓地让父文档去撑大任意一个 iframe。父文档必须靠
  **event.source 与各 `<iframe>.contentWindow 的同一性**自己认领。
- **撑大与还原严格配对**：退出全屏后站点自己的内联样式一字不差地回来。
  `z-index` 写 `2147483647`（32 位有符号整数上限）—— 写成 2147483648
  会溢出成负数（变成最底层）。

### `frameOffset`

文件：`src/content/frameOffset.ts`

职责：把「元素在自己文档里的视口坐标」换算到**提示所在那份文档**的视口坐标系。

⚠️ 换算的终点**不是「顶层文档」** —— 6.1.0 之后这两件事不再是同一个：
提示（调速胶囊、接管提示、引导）住在**当前 realm 自己的 document.body** 上，
而 `position: fixed` 的参照系是**它自己那份文档的视口**。

- 当前 realm 是顶层 → 换算目标就是顶层文档（与 6.0.x 一样）；
- 当前 realm 是 iframe → 换算目标就是那个 iframe 自己的文档。

⚠️ 换算到顶层坐标是**错的**（实测，真实 Chromium）：内容脚本跑在 iframe 里时，
提示也住在 iframe 里，而 iframe 的视口只有 220px 高、视频在顶层 y=360 ——
换算到顶层会算出 `top = 376px`，胶囊被推到 iframe **之外**，用户什么也看不到。

沿 frameElement 逐层向上换算，直到元素所在文档就是**当前 realm 的 document**。
跨域时 frameElement 取不到（访问即抛或为 null），退回未换算的坐标。

⚠️ 缩放：iframe 被 `transform: scale()` 缩过时，它内部的 CSS 像素与父文档的
CSS 像素**不是 1:1**。所以这里返回的是**换算后的完整矩形**（含宽高），
而不是「原矩形 + 一个偏移量」—— 后者在有缩放时根本表达不了正确结果。

`SpeedToast` 与 `TakeoverNotice` 共用这一处实现。

接口是 `topLevelRect(element)`，返回**四个边**而不只是左上角 ——
早先只返回 `top`，于是「视频底边」那类定位（接管提示挂在视频下方）
把未缩放的高度当成了缩放后的高度，位置偏出上百像素。

⚠️ **换算必须考虑 iframe 被缩放**：站点常把播放器 iframe 缩放（`transform: scale(0.5)`），
此时 iframe 内部坐标系与外部坐标系的比例是
`scale = frameRect.width / frame.offsetWidth`（视觉尺寸 ÷ 布局尺寸）。
不乘这个比例，缩放过的 iframe 里的提示会**偏到一半位置**。

⚠️ 缩放比用 `frameRect.width / frame.offsetWidth` 而不是 `getComputedStyle` 的
`transform` 矩阵：`transform-origin` 造成的位移在代数上会与缩放部分抵消，
而「视觉框 ÷ 布局框」这个比值**自动**包含了缩放与原点的影响。

⚠️ iframe 有边框时，内容盒起点是 `frame.clientLeft / clientTop`，不是 0。

跨域 iframe 拿不到 `frameElement`（`window.frameElement` 为 null），
此时循环直接停止，坐标停在那一层 —— 那一层的内容本来也不该被我们接管。

### `overlayLayers`

文件：`src/content/overlayLayers.ts`

职责：

- 找出覆盖在视频之上的浮层，只看视频父容器的**直接兄弟节点**（不做全子树遍历）
- 判据只用结构与几何，**不认任何插件的类名**：绝对/固定定位、与视频矩形相交、
  落在视频范围内、覆盖面积不小于 2%
- 区分两类：
  - `subtitle` —— **墨水**窄、矮、行数 ≤ 2、重心在视频下半部。**跟着视频搬进 overlay**
  - `overlay` —— 其余（弹幕等）。**留在原地**，被 overlay 的不透明背板挡住

**为什么不认类名**：沉浸式翻译用 `.imt-caption-container`，但下一个字幕插件
可能是别的名字，弹幕又完全是另一套。认类名等于和某个插件耦合，它一改类名就又坏了。

**为什么量「墨水」而不是容器宽度（6.0.9 更正）**：字幕容器的宽度是**排版方式**
决定的，不是内容决定的。绝大多数字幕容器写 `left:0; right:0; text-align:center` ——
容器铺满整个播放器（实测 100%），文字却只有中间一小段。拿容器宽度去和视频比，
100% 宽的字幕必然被判成「太宽 → 不是字幕」，于是它根本不搬进全屏，
用户看到的就是「一按 f 字幕就没了」。
现在量的是文字**实际占据**的范围（`Range.getClientRects()`）：
容器宽度是排版的度量，墨水宽度才是内容的度量。

**为什么字幕用「重心」而不是「底边」定位**：站点给播放器的 CSS 尺寸通常小于视频
被全屏放大后的尺寸（实测 640×360 → 1280×720），字幕按 `bottom: 8%` 定位在
**原尺寸**的播放器里，换算到全屏坐标系后底边只落在 46% 处。早先的判据要求底边
在 55% 以下，结果在真实页面上把所有字幕都判成了非字幕。

**字幕搬进 overlay 之后还需要三件事**（缺一个字幕就仍然看不见，
6.0.8 号称修好但实测从未生效）：
1. **z-index 高于视频**：视频 reparent 后带 `z-index: 2147483643`（inline `!important`），
   字幕原本是 `auto` —— z-index 只在**同一层叠上下文**内比较，`auto` 依然输给显式
   高层级的视频。DOM 顺序排在视频之后**不够**。
2. **住在一个与画面等大的定位参照物里**（`[data-vsc-caption-host]`）：
   站点字幕的 `bottom: %` 相对**播放器容器**定位，容器跟着视频一起放大后，
   百分比必须相对**画面框**算而不是视口，否则字幕会掉进黑边里。
3. **参照物必须有真实尺寸**：它是 stage 的 flex item，而 flex item 的宽度默认由
   内容决定 —— 里面只有绝对定位的字幕（不参与布局），于是它塌成 0 宽，
   站点字幕的 `left:0; right:0` 相对 0 宽包含块 → **字幕自己也是 0 宽** →
   一个像素都看不见。必须显式给 `width/height: 100%`。

**参照物的尺寸是算出来的，必须跟着视口重算**：视频是 `object-fit: contain`，
画面框（视口里实际显示的那块矩形）取决于**视口**尺寸与视频固有宽高比。
`alignStageToVideo()` 按这个比例算出画面框并写成参照物的 px 尺寸。

- 视口变了（用户拖窗口、旋转手机、移动端地址栏收起）→ 画面框变 → 参照物必须跟着变。
  早期只监听了 video 自己的 `loadedmetadata` / `resize`（那是**媒体**尺寸变化），
  视口变化两者都不触发，参照物永远停在旧值上：实测 1280×720 视口下的 4:3 视频
  参照物是 960×720，窗口缩到 900×600 后画面框变成 800×600，参照物还停在 960×720
  → 字幕的 `bottom: 5%` 相对 720px 算，底边落在 635px，**已超出 600px 的视口**。
- 拿不到视频固有尺寸（`videoWidth` 为 0）时必须**显式**退回铺满视口，
  而不是直接 return —— 否则参照物会停留在**上一个视频**的尺寸上。

**控制条给字幕的避让位移必须可精确还原**（`src/content/subtitleOffset.ts`）：
控制条与字幕都贴着画面底部，控制条出现时要把字幕往上抬。但字幕是**站点自己的
节点**，站点常在它身上写 `transform`（`translateY(-50%)` 居中、`scale()` 动画）。

- 必须记**计算值**（`getComputedStyle`）而不是内联值 —— 站点的 transform 可能写在
  样式表里，内联值是空的。
- 还原时写回 `!important` 内联，值就是记下来的那个计算值。
- 我们的位移与站点的位移**叠加**（`base translateY(-40px)`）而不是互相覆盖。
- ⚠️ 内联与样式表两种写法**必须分开测**：同时存在时会互相掩盖 ——
  删掉我们写的内联后样式表那条会接管，计算值照样对，用例变成假通过。

### `viewportRoot`

**浮层挂在哪儿**，以及为什么不能挂在 `<body>` 上。

一条 CSS 规矩：**祖先只要带 `transform` / `filter` / `perspective` /
`backdrop-filter` / `contain` / `will-change`，它就成了 `position: fixed`
后代的包含块** —— 于是 `fixed` 不再相对视口，而是相对那个祖先的盒子。

`body { transform: translateZ(0) }` 是站点做 GPU 加速的常见写法。
浮层挂在 body 上时全部中招（实测：视频 top=850、控制条 top=2334、
退出钮 top=2360，视口只有 700px 高 —— 用户看到一片黑，连退出按钮都没有）。

transform 只会让自己成为后代的包含块，**不会传染给父元素** ——
所以规则只有一条：**浮层挂在 `<html>`（`document.documentElement`）上**。

顺带躲开三件事：

| | 挂在 `<body>` | 挂在 `<html>` |
| --- | --- | --- |
| 站点给 body 加 transform | ❌ 全屏报废 | ✅ 免疫 |
| 站点 `document.body.innerHTML = ''` | ❌ 节点被一起带走 | ✅ 安然无恙 |
| 站点的 `body > *` 选择器 | ❌ 会命中我们 | ✅ 命中不到 |
| 站点的 `html > div` 选择器 | ✅ 命中不到 | ❌ **会命中我们** |

最后一行是 6.2.0 那个回归的根因 —— 挂到 `<html>` 之后，**我们成了
`<html>` 的直接子节点**，于是站点「只认我自己的顶层节点」的那类规则
（`html > div` / `html > *`）改成了**冲着我们来的**。
所以挂载点换了之后，**隔离策略必须跟着换**（见下一节）。

**约束**：

- 浮层**一律**用 `mountViewportRoot()` 挂载，不许直接 `document.body.appendChild`。
- `position: fixed` 的浮层只能这样挂 —— 相对 body 的 `fixed` 是**假的 fixed**。
- 唯一例外是**读屏播报通道**（`liveRegion`）：它的位置对读屏毫无影响
  （视觉上只有 1px 且被裁掉），而留在 `<body>` 里对读屏器更常规。
- 因为浮层成了 `<html>` 的直接子节点，**DOM 观察只能看 `<html>` 的直接子节点**
  （见 `BodyObserver` 一节）：看子树的话，我们自己挂/摘浮层就会被算成
  「页面内容变了」，每次浮层显隐都推进一次缓存代次。

**已知限制**：站点给 **`<html>` 本身**加 transform 时仍会中招。
现实中几乎见不到 —— 那样做的话站点自己的 sticky 头部与滚动条早就乱了，
是它自己先坏。真遇到了只能退化（网页全屏退成原生全屏）。

#### 挂到 `<html>` 之后，为什么**还要** inline 隔离

**一句话**：挂载点决定浮层「在哪儿」，隔离决定浮层「长什么样」——
**挂到 `<html>` 解决的是前者，后者要另有一套机制。**

**级联上的事实**（CSS Cascade 4）：

| 声明 | 优先级 |
| --- | --- |
| 作者 `!important`（站点写的 `html > div { display: none !important }`） | 高于下面两条 |
| **内联 `!important`**（`element.style.setProperty(…, 'important')`） | **最高**（style 属性高于任何选择器） |
| 作者普通声明（**我们注入的那份 `<style>`**） | 最低 |

于是：**我们注入到页面里的那份 `<style>` 只是普通作者声明** ——
站点一条 `html > div { display: none !important }` 直接赢过它。
这正是 6.2.0 回归的症状：

```
[html>div] {"overlayDisplay":"none","controlsDisplay":"none","videoInStage":false}
→ 视频退回 css-cover、页面滚动锁死，但没有控制条、没有退出按钮（只剩 Esc 能退出）
```

**三套隔离，三种形态**（都在写内联 `!important`）：

| 浮层 | 隔离入口 | 说明 |
| --- | --- | --- |
| 五个页面级提示（胶囊 / 角标 / 接管提示 / 引导 / 扩展已更新） | `isolateNotice()` | `all: initial !important` + `NOTICE_SHELL_STYLES` |
| 网页全屏背板 + 舞台 | `isolateFullscreenOverlay()` | `all: initial !important` + `OVERLAY_ISOLATION_STYLES` / `STAGE_ISOLATION_STYLES` |
| 控制条**宿主** | `isolateControlsHost()` | `all: initial !important` + `CONTROLS_HOST_STYLES` |

**为什么控制条宿主也要**：shadow root 是一条**结构性**的边界，但它只护住
**里面** —— 宿主自己仍是 light DOM 里的一个 `div`，
站点的 `html > div { … !important }` **命中的就是宿主本身**。
（`:host { all: initial; … }` 只隔离了继承属性与宿主自身，**挡不住**
一条命中宿主的 `display: none !important`。）宿主因此也必须有一份内联底座。

**`display` 必须**跟着状态**内联切换**（`setOverlayActive()`）：
class 只能改**样式表**里的规则，而那是普通作者声明 —— 撤掉 `.vsc-active`
并不能保证背板真的 `display: none`（站点一条 `html > div { display: block !important }`
就能把它钉住）。class 照旧增删（它是「此刻处于网页全屏」的标记，
单测与 e2e 都按它判断），但**真正生效的是内联的那一份**。

**铁律**（与页面级提示同源）：写在这三个浮层上的内联样式**必须带 `!important`** ——
隔离底座里的 `all: initial !important` 会把**普通的**内联声明整个抹掉
（少了 `!important`，连 `position` 都会一起没掉）。

**单一真源**：控制条宿主的样式表由 `CONTROLS_HOST_STYLES` **生成**
（`:host { … }` 与内联底座共用同一张表），改一处忘另一处 = 隔离破功。

守卫：`tests/e2e/fullscreen-isolation.spec.js`（真实 Chromium，
页面带 `html > div { display: none !important }`）+
`src/content/runtimeStyles.test.ts` / `controlsStyles.test.ts` /
`fullscreenController.test.ts`（内联声明带不带 `!important`）。

### `domMatches`

**页面可以把 `Element.prototype.matches` / `closest` 改坏** ——
换成会抛异常的版本，或者直接删掉。这不是理论：任何脚本都能这么干。

而这两个方法出现在**核心路径**上：

| 调用点 | 抛了会怎样 |
| --- | --- |
| 「站点有没有点名这条视频」（接管 / 引导判定） | 整条候选扫描抛掉 → **快捷键彻底失灵**（用户看到的是「扩展等于没装」） |
| 「用户当时点的是哪条视频」（手势证据） | 视频拿不到「用户碰过它」两条证据 → 被判成装饰物 → **既不接管，也不弹引导** |
| 「这一层是不是我们自己的浮层」（字幕层探测） | 一路冒到 `enter()` → **网页全屏整个进不去** |

所以生产代码里**不许裸调**这两个方法，一律走这里：

- `matchesSelector(element, selector)` → 判不出来就当**不匹配**；
- `closestSelector(element, selector)` → 判不出来就当**没有**；
- `probeClosest(element, selector)` → **三态**（`found` / `absent` / `unknown`），
  给「要的是能不能排除掉」的场景用（字幕层探测：判不出来时保守地
  当成「排除不掉」—— 宁可少搬一层字幕，也不能把控制条或背板搬进画面里）。

**结构守卫**：`src/shared/domMatches.test.ts` 会扫 `src/` 下的生产代码，
发现任何裸调的 `matches(` / `closest(` 就红 ——
这类失败用户完全看不出来（他只看到「按了没反应」），
所以要在写出来的那一刻就被挡住。

## 站点适配

文件：`src/content/siteAdapters.ts`

当前有七类适配：`generic` / `youtube` / `bilibili` / `iqiyi` / `v.qq.com` /
`youku` / `mgtv` / `localhost`（含 `127.0.0.1`）。

适配器只负责两件事：**优先选择器**（`selectors`）与**主播放器**（`mainSelectors`）。
reparent 的可行性判断在 `FullscreenController.enter()` 内统一完成。

- `selectors` 最后一档是 `'video'` —— 匹配页面上每一个视频，作为兜底。
- `mainSelectors` 必须指向**具体**的选择器。它给的是「主播放器豁免」：
  站点点名了谁，装饰性判定（见 VideoRegistry 一节）就不适用于它。
  爱奇艺的豁免是实测出来的：它的主播放器形状是 `autoplay` + 无 `controls`，
  与装饰性预览在 DOM 上一模一样，没有这条豁免就整页失键。

⚠️ 域名匹配**必须是后缀**。曾经用 `hostname.includes('youtube.com')` ——
那会把 `notyoutube.com` 也当成 YouTube，于是它拿到了主播放器豁免
（= 装饰性判定失效），而键盘控制器那边用的是严格后缀正则，
同一个域名在两条路径上被分成两类视频 —— 这正是「图标和快捷键表现不一致」的来源。
现在统一用 `/(^|\.)example\.com$/`。

⚠️ 腾讯 / 优酷 / 芒果的选择器**未在真实站点验证过**（只有爱奇艺是拿真实站点量的）。
没有豁免时它们退回通用兜底，行为与今天一致，不会更坏 —— 但上线前应人工确认。

## 几条判据（6.2.0 审计沉淀）

这一节记的不是「我们修过哪些 bug」，而是**几条会反复咬人的判据**。
它们都来自实测，每一条都对应一次「看起来对、其实没生效」的失败。

### 1. 观察器绑在元素上，不是绑在文档上

`MutationObserver` 观察的是**一个元素**。站点把那个元素换掉（`body.replaceWith`），
观察者就成了孤儿 —— 它再也收不到任何通知，而旧元素再也不会变化。

判据：**任何观察器都要问一句「我观察的东西会不会被换掉」。**
会被换掉的，观察点要上移到「换掉它的那一层」（见 `BodyObserver`）。

### 2. 「状态结束」不一定产生 DOM 增删

退出网页全屏时，背板**没有被摘掉** —— 只移除了 `vsc-active` class。
所以任何「观察子节点增删」的实现都收不到「退出全屏」这个信号。

判据：**判断某个状态是否结束，先问「它的结束会不会产生 DOM 变化」。**
不会的话，就得观察那个状态**自己的载体**（class / 属性），或者让产生它的那一端主动通知。

### 3. class 改不了 `display`，样式表声明也输给作者的 `!important`

`class` 只能改**样式表里的规则**。而样式表声明是普通作者声明 ——
站点一条 `html > div { display: none !important }` 就赢过它。

判据：**要赢过站点的样式，只能用内联 `!important`**（它赢过任何作者 `!important`）。
浮层的隔离底座因此是内联的，且 `:host` 规则与内联底座**共用一张表**生成。

### 4. 观察者要看对那一层

观察 `<html>` 的**子树**会把我们自己挂/摘浮层算成「DOM 变化」；
观察 `body` 的子树则**看不到**挂在 `<html>` 上的东西（网页全屏背板就在那儿）。

判据：**先画出「谁挂在哪儿」，再决定观察哪一层。** 观察面要刚好够，
多一层会自激，少一层会漏。

### 5. 守卫要量「用户真正看到的东西」

这一轮修掉的缺陷里，有好几个是**假守卫**放过的：
断言「节点还在 DOM 里」（但它 opacity 是 0 / 看不见）、
断言「某个函数被调用过」（但结果被丢弃）、
用 200ms 轮询采样（采样点永远落在「只有一条」的时刻上 → 恒绿）。

判据：**守卫量的是 computed style、真实的 textContent、真实的焦点、
真实的 `chrome.action.getTitle()` 返回值** —— 不是「元素存在」或「函数被调用」。
轮询式守卫必须同时断言「至少采到过一次」。

### 6. 没有 CAS 的地方，「写后读回」不等于「只有一方赢」

`chrome.storage.local` 没有 compare-and-set。写后读回只能判出**已落盘**的覆盖，
而竞争者的写可能还在路上 —— 那一刻读回来的仍是自己的值。

判据：**先确认存储有没有原子原语。** 没有的话，
写后要等一段稳定窗口再读回，且读失败一律**放行**（宁可多弹一次，
也不要让「存储坏了」变成「功能再也不出现」）。见 `createStorageClaimBroker`。
