# 2026-10-23 竞品分析 + 商店页实读（Video Speed Controller 6.2.0）

## 一、对话出发点

Jasper 的三个请求（同一轮会话）：

1. 「对当天项目进行一次体检，并告知项目状态是否正常，能否推送到 Chrome 仓库使用。」
2. 「我可以检索市面上同类型的插件，并从产品角度分析我们当前插件的优势和特点。
   **至少要有优势，或者具备特点，否则大家凭什么使用我们？**」
3. 「可以的，先做你能做的。还有，代码都推送到仓库了吗？」

第 2 条是本轮主线。那句反问（"大家凭什么使用我们"）是这个项目的真问题：
工程投入已经超前于市场验证，而**商店页实读下来是 23 用户 / 0 评分**。
所以我这次不是去写「我们的功能列表」，而是去回答「凭什么」——
如果答案撑不住，就直说撑不住。

- **动机**：PRODUCT.md 阶段 0 定的唯一优先级是拿用户信号（4 周分叉判据 2026-11-03），
  但「零推广 → 23 用户 → 无法区分是产品不行还是没推过」是个死循环。
  竞品分析能打破它的一半：**如果竞品在同一定位下能做到 10 万用户**，
  那 23 用户就归因于分发，不是产品。
- **我的解读**：找**真正的替代品全集**（不只是同类关键词命中），
  从产品角度给出优势与特点，并把差距**并排写**出来，不做自说自话。
- **不做的事**：不改产品代码、不加功能、不上传商店。

## 二、Phase 0（deep-research skill 强制）：三个方向分叉点

按 skill 要求，先问后搜。Jasper 三个都选了「最狠的那个」：

| 维度 | 选项 | 选定 |
|---|---|---|
| 产出用途 | 决策分析 / 落地文案 / 都要 | **只要决策分析** |
| 对标范围 | 直接同类 / 头部 / **真正的替代品全集** | **全集** |
| 差距章节 | 不写 / 简写 / **并排写** | **并排写** |

「全集」这个选择直接把研究面从「倍速插件」扩到了「网页全屏播放器」，
也把天花板判断从「同类里排第几」变成了「这个位置值多少钱」。

## 三、方法与降级（重要，先说清楚这次拿不到什么）

**能拿到的（一手）**：
- Chrome Web Store 官方 RPC（`QcU9bc`）搜商店、
- 每个商品的商品页（Playwright 渲染后读 DOM，拿到评分/用户数/版本/分类/相关推荐）、
- 竞品的**评论本体**（含 1 星差评原文）、
- Chrome for Developers 官方文档（排序机制、商店政策）。

**拿不到的（降级，如实记在 Methodology）**：
- `WebSearch` 在本环境不可用（"web-search access isn't available"）；
- exa 配额耗尽；chrome-stats.com 返回 403。
- → 因此**没有 Tier-2 媒体评测**这一层证据，
  结论是「商店内证据（Tier 1）+ 官方文档（Tier 1）+ 代码实测（Tier 1）」三线交叉。

一个具体的坑：`curl chromewebstore.google.com` 返回 0 字节（SSR 是空的），
一开始以为被反爬。实际是**必须渲染**。改用 Playwright MCP 后全部页面都能读到。
这条方法论值得留在仓库里——**商店数据只能靠渲染取，curl 拿不到**。

## 四、核心发现

### 4.1 赛道结构（高置信）

| 位置 | 商品 | 用户数 | 评分 |
|---|---|---|---|
| 头 | Video Speed Controller (igrigorik) | 300 万 | 4.0 / 4.5K 评论 / Featured |
| | Global Speed | 70 万 | 4.5 |
| | Super Video Speed | 30 万 | — |
| | HTML5 Video Speed Control | 4 万 | 2022-03 起停更 |
| **我们的定位** | 网页全屏播放器 | **天花板约 10 万** | Full Screen for Google Chrome 仅 3.4 分 |
| 定位最近的 | Video Maximizer | 2 万 | 4.8 |
| **反例** | Zoom Video - UltraWide Fill | **40 万** | — |

两个结论直接决定定位：
1. **我们所在的品类天花板约 10 万**（不是百万赛道）。
2. 但「去掉黑边 / 铺满窗口」这个**更大的需求有 40 万**——
   问题不是需求不存在，是**我们没占那个词**（且那个需求比"播放器"更简单）。

### 4.2 我们的基线：23 用户 / 0 评分 —— 但这不能证明"产品没优势"

商店页实读（2026-10-23）：23 users、0 out of 5、"No ratings"、v6.0.8、
40.14 KiB、2 种语言、Tools 分类。

Chrome 官方文档明说排序吃 "ratings from users as well as usage statistics"。
→ **0 评分 = 排序里没有我们**。这是**冷启动死锁**，不是产品判负。

### 4.3 最重要的发现：商店页简介是**反的**

线上英文简介里有两句是错的：

| 线上写的 | 实际是 |
|---|---|
| `Customize four shortcuts from the options page` | 实际 **7 个**可改绑动作（`SHORTCUT_DEFINITIONS`） |
| `Cross-origin iframe videos may not be directly controllable` | 6.1.0 起**完全支持**（`manifest.content_scripts[0].all_frames = true`） |

第二句尤其致命：**我们把最大的技术优势写成了缺陷**。
而这行字**从未出现在仓库任何版本里**（`git log -S` 全历史为空）——
说明它是发布时在 Dashboard 手打的，之后再没同步过。

> 竞品 Video Maximizer 评分的核心是「能跨域 iframe 接管」，
> 我们**做到了却写在简介里说做不到**。

### 4.4 我们的优势清单（可验证，不是形容词）

- **跨域 iframe 接管**（6.1.0 全量修好）——竞品商店描述里没有一家提
- **非 QWERTY 布局**——竞品评论里被骂"assuming my keyboard layout is QWERTY"，
  我们按字符绑定（`src/shared/shortcuts.ts` 有实测记录）
- **接管判据是证据分层**（P0/P1/P2），不是"抢所有 video 元素"——评论里最常见的
  "broke the website" 类投诉我们从设计上避开了
- **零遥测、零账号、开源**——竞品 globalSpeed 有"把用户链接送去服务器"的历史争议
- **常驻角标**（不是 3 秒消失的 toast）

### 4.5 诚实的三条限制

1. **我们的优势是防守型的**——竞品没有的我们有，但**用户看不出来**
   （"跨域 iframe 能接管"是"不出事"，不是"多一个功能"）。
2. **23 用户不能证明产品没优势**——但也**不能证明有优势**，因为从未推广过。
3. **减法哲学 vs 市场投票**：第三方统计里"学习工作流"（字幕/笔记/生词卡）跑到 3–10 万用户，
   而我们的答案是"不做"。这个矛盾没有调和，只能由 Jasper 定。

## 五、发现之后做了什么（不只是写报告）

### 5.1 把"商店文案 ↔ 真实能力"的漂移变成**可执行的守卫**

这是本轮唯一的代码改动，也是最值得留痕的部分。
问题不是"文案过时"这一次，是**这类漂移没有机制拦**——
商店简介是手打的，能力是代码里的，两者之间没有连接。

在 `scripts/release-content.test.ts` 加了一条守卫组（4 条）：

1. 详细描述正文找得到（中英各半）
2. **可改绑动作数必须等于 `SHORTCUT_DEFINITIONS.length`**（中英文案都要对）
3. 详细描述里不许出现过时说法（`may not be directly controllable` /
   `customize four shortcuts` / 中英两版"嵌入框管不了"）
4. 描述里承诺了跨域 iframe 支持 → `manifest.content_scripts[0].all_frames` 必须是真的

顺手把原来那条 markdown 星号测试重构成共用 `locateDetailedDescription()` helper，
避免两处各自找锚点、以后再漂移。

**8 组变异验证**（改坏实现 → 确认守卫变红 → 恢复 → 确认绿）：
M1 动绑键数 / M2 英文正则 / M3 英文过时句 / M4 中文过时句 / M5 中文"管不了"句 /
M6 跨域承诺与 manifest 不一致 / M7 中文数字→英文数字映射 / M8 锚点漂移。
**M5 第一版是死的**（只写了英文正则），补了中文正则才真正变红。

⚠️ 过程中踩到：变异判定脚本只看 vitest 输出的 `tail -6`，
把 "Failed Tests" 那几行截掉了 → 误判成"守卫是死的"。
改成 grep 全文 `Tests +[0-9]+ failed` 之后才看清真相。

## 八、踩过的坑（给下一个人）

1. **`curl` 拿不到商店页**——SSR 返回 0 字节，必须用真实浏览器渲染后读 DOM。
2. **商店搜索 RPC 不是公开 API**——`POST .../data/batchexecute?rpcids=QcU9bc`，
   body 是 `f.req=[[["QcU9bc","[\"<query>\"]",null,"generic"]]]`。
3. **CWS API 没有 listing 元数据接口**——v2 只有 upload / fetchStatus / publish /
   cancelSubmission。改简介、分类**只能人工去 Dashboard 点**。
4. **我们的商店页页底在替竞品做转化**——"You might also like…" 推的是四个有评分的竞品。
   搜索卡片只显示名称 + 评分 + Featured（不显示用户数），所以我们显示 "0 out of 5"。
5. **变异判定的输出不能只看尾巴**——必须 grep 全文找 `Tests N failed`。
