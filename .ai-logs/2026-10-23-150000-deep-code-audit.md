### 2.4 过程中踩到的坑（重要）

- **我自己的变异脚本一度把 `src/content/videoRegistry.ts` 写坏了**（2934 行 → 截断）。
  用 `git checkout --` 恢复。教训：变异脚本必须先备份、且断言「模式确实匹配到」，
  否则一次 replace 没命中就会静默留下半个文件。
- **有一轮变异判定是假绿**：python 脚本里 `import sys` 漏了，
  变异根本没生效，测试当然全绿。差点把「测试无效」记成「测试有效」。
- **grep 模式漏判**：vitest 输出里 `× ` 与 `✓` 混排，
  我用 `grep -E "× |Tests "` 连续几次漏掉了红的那条。
  最后统一改成 `grep -E "Failed Tests|FAIL|Tests  "` 才可靠。
- **守卫自己有自证陷阱**：第一版「阈值常量必须被测试引用」搜的是整个文件文本，
  于是「注释里提一句常量名」就能通过；而且它把**自己**也当成引用者（清单里就写着名字）。
  修法：剥掉注释 + 排除本文件。修完又做了 4 组负向验证。

### 2.5 一个源码注释被实测推翻

`runtime.ts` 里 `FOCUS_WATCH_INTERVAL_MS` 的注释写着：

> 「焦点移进**子 iframe** 时，顶层文档收不到 focusout —— 它只是发现自己的
> activeElement 变成了那个 `<iframe>` 元素。」

用 Playwright 在真实 Chromium 实测（聚焦一个 iframe 元素）：

```
顶层收到的事件序列：blur:INPUT → focusout:INPUT → focus:IFRAME → focusin:IFRAME
```

顶层**收得到** `focusin:IFRAME`，捕获阶段监听器会拿到，
`reportFocus()` 那时判 `ownsUserFocus()` 为 false → 主动 `releaseFocus()`。
也就是说这个场景里焦点事件已经挡住了，「顶层一直以为焦点在我这儿」不会发生。
已按实测改写注释，说明巡检真正的职责是**兜底** + **上下文失效的周期性发现途径**。

`origin/main` 上从 2026-10-22 03:50 起，**连续 8 次 run 全是 failure**，
而 10-08 之前连续 success。中间只隔了「审计驱动的几轮修复」。

判据 13（先分清产品回归与测试环境自身）在这里**不够用**：

三个 job 各挂各的：

| job | 失败原因 | 类别 |
|---|---|---|
| Unit Tests | `launch.js` 顶层检查 `dist/manifest.json` → `--list` 收集用例时报错 | **绑错了位置** |
| Build | skipped（被上游的失败挡住） | — |
| Real Extension E2E | 3 条断言绑死机器语言 | **绑死了语言** |

### 根因 1：Unit Tests job 不跑 build，而守卫需要 dist/

`scripts/ci-workflow.test.ts` 有一条守卫要跑 `playwright test --list`
（核实「登记进 `test:e2e:ext` 的 spec」与「Playwright 真会跑的 spec」
是不是同一份）—— 那条守卫活在 Unit Tests job 里，
而那个 job **不跑 build**（build 是另一个 job）。

于是 `tests/e2e/helpers/launch.js` 在**模块顶层**的 `dist/manifest.json` 检查
抛错 → `--list` 收集用例时报错 → 守卫炸掉 → 整个 job 红。

⚠️ 症状极具误导性：报错写着「扩展构建产物不在 …——先跑 pnpm build」，
而 Unit Tests job 里**根本没有 build 这一步** ——
读起来像「CI 配置漏了一步」，实际是那条检查**放错了位置**。
而 `--list` 根本不需要扩展产物：它只要知道有哪些 spec 文件。

修法：检查改成**惰性**（`assertDistReady()` 在真正启动浏览器时才调）。
验证：`mv dist /tmp/…` 后 `--list` 正常列出 31 个 spec、0 errors。

### 根因 2：三条断言绑死了机器语言

`chrome.i18n` 挑哪个 locale 目录跟的是**系统 locale**（不是界面语言），
开发机是中文系统、CI 容器是英文环境 —— 两者**本来就不同**。

| 用例 | 旧写法 | 在英文下为什么必然失败 |
|---|---|---|
| `options-page` AX tree | 「把名字里所有 `f` 删掉看剩下什么」 | 动作名 "Page fullscreen" → "Page ullscree: "，断言 "Page ullscreen:" 匹配不上 |
| `options-layout` 加长文案 | 塞**一段中文**重复三遍 | 原文本本就是英文（本来就长），中文加长三倍不成比例 → 页面压根没被撑高（`scrollHeight 800 == clientHeight 800`），前置条件就挂了 |
| `first-run-hint-content` 4 行 | 断言**渲染**恰好 4 行且不折行 | `hintMore` 英文 97 字符、卡片 `max-width` 只有 560px → **必然**折成 2 行（实测：源码 4 段、渲染 5 行、最差折 2 行） |

第三条的注释里写着「折行会让渲染行数变多，而阅读窗口是按源码行数算的」——
但断言偏偏查的是渲染行数。承重不变式是**源码行数**
（`readWindowMs` 按 `text.split('\n').length` 算阅读窗口），渲染折行**不影响**它。
改成：源码恰好 4 段 + 任何一段最多折 3 行。

⚠️ 本地无法复现英文环境（`--lang` 与 `LANG` 都固定不了扩展 i18n ——
`chrome.i18n` 跟系统 locale 走，见 `src/shared/i18n.ts` 的 currentLocale 说明）。
**替代验证**：把英文文案塞进同样约束的容器里量，
测出「源码 4 段 / 渲染 5 行 / 最差折 2 行」——
与 CI 报的 5 行吻合，且新断言在英文下必然成立。

⚠️ 这已是这个仓库**第三次**栽在「断言写死语言」上（2026-10-06 一次）。
所以这次修的是**断言的写法**（从 locale 文件取文案），不是再加一条特判。
